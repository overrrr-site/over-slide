# Over-Slide 精度向上設計書：リーダーAI導入 + Step 6 削除

## 背景と目的
over-slideの出力精度を上げるため、以下の2つの施策を行う：
1. **リーダーAI（部分リーダー）の導入** — ステップ間の整合性と指示解釈の精度を向上
2. **Step 6（デザインレビュー）の削除** — 機能していないステップを除去し工程を簡素化

## 決定事項
- **モデル配置**: リーダー = Opus（判断力最優先）、作業AI = Sonnet（実行）
- **Step 6**: 削除（テキストデータしか見ておらず、見た目のレビューができていない）
- **インターフェース**: チャットを1つに統合（リーダーAI）、表示エリアは各ステップのものを残す
- **6ステップ → 5ステップ + リーダー** に再構成


### 現状の問題点

**問題1: ステップ間の断絶**
- Step 2で構成を変更 → Step 3の詳細は古いまま
- 各AIは自分のステップしか知らない。変更の影響を判断できない

**問題2: レビュー結果の活用が手動**
- 「3ページ目のデータが弱い」→ ユーザーが手動で修正指示を考える必要がある

**問題3: 文脈の劣化**
- ステップが進むごとに、元のリサーチ情報から遠くなる

**問題4: Step 6が機能していない**
- テキストデータしか渡されず、見た目（色・余白・フォント）は見えない
- Step 4のカテゴリ名を変えただけの重複

## 2. 新しいフロー

### 2-1. アーキテクチャ

```
┌──────────────────────────────────────────────────────────────┐
│                    ユーザーの指示                              │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────────┐
│  ★ リーダーAI（Opus）— ユーザーとの唯一の対話窓口              │
│                                                              │
│  役割:                                                       │
│  ① 意図の解釈 — 何をしたいか、どのステップの話か                 │
│  ② 影響範囲の判断 — 他ステップへの波及があるか                   │
│  ③ 確認 — 影響が大きければユーザーに聞く                        │
│  ④ 実行指示 — 適切なステップのAIに具体的な指示を出す             │
│  ⑤ 結果チェック — 整合性確認・次のアクション提案                 │
│                                                              │
│  入力: 全ステップの要約 + ユーザー指示                          │
│  モデル: Opus                                                 │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
    ┌──────────┬──────────┬──────────┬──────────┐
    ▼          ▼          ▼          ▼          ▼
 Step 1     Step 2     Step 3     Step 4     Step 5
 リサーチ    構成       詳細      レビュー    デザイン
 (Sonnet)   (Sonnet)   (Sonnet)  (Sonnet)   (Sonnet)
    │          │          │          │          │
    └──────────┴──────────┴──────────┴──────────┘
                       ▼
              リーダーAI（結果チェック）
                       ▼
              ユーザーに結果を返す
```

### 2-2. UI構成

```
┌──────────────────────────────┬────────────────────┐
│                              │                    │
│  表示エリア（左）              │  チャット（右）      │
│                              │                    │
│  リーダーが作業中のステップに    │  リーダーAI（Opus）  │
│  応じて自動で切り替わる         │  = 唯一の対話窓口    │
│                              │                    │
│  表示されるもの：              │  ユーザー：          │
│  ・リサーチメモ               │  「構成見せて」       │
│  ・構成一覧（並替え可能）      │                    │
│  ・ページ詳細                 │  リーダー：          │
│  ・レビュー結果               │  「今の構成です。     │
│  ・スライドプレビュー          │   変更しますか？」    │
│                              │                    │
│  ※ 既存の各ステップの          │                    │
│    表示コンポーネントを再利用   │                    │
│                              │                    │
└──────────────────────────────┴────────────────────┘
```

**ポイント:**
- チャットは1つだけ（リーダーAIと会話）
- ユーザーはステップを意識しない。リーダーが自動で振り分ける
- 表示エリアは既存のステップごとの表示部品を再利用
- リーダーが「今は構成の話をしている」と判断したら、左側に構成一覧を表示

### 2-3. モデル配置

| 役割 | 現状 | 変更後 | 理由 |
|------|------|--------|------|
| リーダー | なし | **Opus** | 曖昧な指示の解釈・影響判断に最高の推論力が必要 |
| リサーチ | Sonnet | Sonnet | 変更なし |
| 構成 | **Opus** | **Sonnet** | リーダーが判断するので、構成AI自体はSonnetで十分 |
| 詳細 | Sonnet | Sonnet | 変更なし |
| レビュー | **Opus**/Gemini/GPT | **Sonnet** | リーダーが品質管理するので、レビュー単体はSonnetで十分 |
| デザイン | Sonnet | Sonnet | 変更なし |

**効果:** Opusの使用をリーダーに集中させることで、全体の判断精度が上がる。コストは同等かやや削減。

## 3. リーダーAIの詳細設計

### 3-1. リーダーが受け取る情報

リーダーは **全ステップの要約** を常に持つ（詳細データは持たない）：

```
{
  "project_summary": {
    "brief": "（ブリーフシートの要点 200文字程度）",
    "research_status": "完了 / 3セクション / 最終更新: 2日前",
    "structure_status": "完了 / 12ページ / 最終更新: 1日前",
    "details_status": "完了 / 12ページ中10ページ作成済",
    "review_status": "完了 / スコア82点 / 改善項目5件",
    "design_status": "完了 / 12スライド生成済"
  },
  "step_summaries": [
    "Step 1: リサーチメモ完了。主な発見: ...",
    "Step 2: 12ページ構成確定。特徴: ...",
    ...
  ],
  "recent_changes": [
    "Step 2: 3ページ目の構成を変更（データ重視に）",
    ...
  ]
}
```

### 3-2. リーダーの処理フロー

```
ユーザー入力
    ↓
[1] 意図分類
    リーダーが判断: 「これは何のリクエストか？」
    → 新規作成 / 修正 / 確認 / 質問 / 次ステップ進行
    ↓
[2] ステップ特定
    「どのステップに関わるか？」
    → 単一ステップ / 複数ステップ / 全体
    ↓
[3] 影響範囲チェック
    「このステップを変えると、他に影響するか？」
    → 影響なし → そのまま実行
    → 影響あり → ユーザーに確認
    ↓
[4] 作業AIへ指示
    リーダーが具体的な指示を作成して作業AIに渡す
    （ユーザーの曖昧な指示を、作業AI向けの明確な指示に変換）
    ↓
[5] 結果チェック
    作業AIの出力をリーダーが確認
    → 問題なし → ユーザーに返す
    → 整合性の問題あり → 追加の修正を提案
    ↓
[6] 表示切替
    リーダーが適切な表示エリアを選択
    → 構成の話 → 構成一覧を表示
    → デザインの話 → スライドプレビューを表示
```

### 3-3. リーダーが特に効く場面

| 優先度 | 場面 | 今 | リーダーあり |
|--------|------|-----|------------|
| 1 | レビュー結果→修正 | ユーザーが手動で修正指示を考える | リーダーが自動変換 |
| 2 | 構成変更→詳細連動 | 詳細は古いまま | 「詳細も更新しますか？」 |
| 3 | リサーチ追加→反映 | 下流に反映されない | 「どこに活かしますか？」 |
| 4 | 全体品質監視 | 各ステップ個別 | トーン・ストーリーの一貫性チェック |

## 4. Step 6 削除の根拠

### 調査結果
- Step 6のAIに渡されるのは **テキストデータのみ**（Step 4の pageContents と同じ構造）
- HTMLソースコードは文字列として渡されるが、**レンダリング結果（色・余白・フォント）は見えない**
- レビューカテゴリが「レイアウト」「視認性」と名前が変わっているだけで、**実質Step 4の重複**
- 削除しても、Step 5のチャット修正（APPLY対応）は残るので、デザインの微調整は可能

### 削除対象ファイル
- `/app/api/ai/design-review/` — API ルート
- `/lib/ai/prompts/design-review.ts` — プロンプト
- `/app/(app)/projects/[projectId]/design-review/` — UI

## 5. 実装ロードマップ

### Phase 1: Step 6 の削除（小さく始める）
- Step 6 の UI・API・プロンプトを削除
- ナビゲーションを5ステップ構成に変更
- Step 5（デザイン）完了後のフロー調整

### Phase 2: 単一チャット + リーダーAIの導入
- 新しいチャットUI（左:表示エリア / 右:リーダーチャット）
- リーダー用プロンプト作成（意図解釈 + 影響判断 + 整合性チェック）
- リーダー = Opus、各ステップ = Sonnet に変更
- 表示エリアの自動切替ロジック
- 既存の各ステップ表示コンポーネントの再利用

### Phase 3: ステップ間の連動
- 構成変更時に詳細の影響チェック
- レビュー結果を修正指示に自動変換
- 影響範囲が大きい場合のみユーザーに確認

### 主な対象ファイル
- `/app/api/ai/project-chat/route.ts` — リーダーレイヤーの追加場所
- `/lib/ai/prompts/` — リーダー用プロンプトの追加
- `/app/(app)/projects/[projectId]/` — 新しいUI構成
- `/app/api/ai/design-review/` — 削除対象
- `/lib/ai/prompts/design-review.ts` — 削除対象
- `/app/(app)/projects/[projectId]/design-review/` — 削除対象

## 6. 検証方法
- 既存のプロジェクトで、リーダーあり・なしで同じ指示を出して出力を比較
- レビュースコアの変化を追跡
- ユーザーの手動操作回数（ステップ間の行き来）が減るかを確認
- Step 6 削除後にユーザー体験が悪化しないことを確認
